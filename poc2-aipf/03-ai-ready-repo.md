# AIPF: AI-Ready Repository Standard

This document defines what a project's repository must provide before an agent team on the AI platform (AIPF) can work on it. It is for technical leads who prepare projects. The rule behind it is simple: **if a new developer needs two days of help to run the project, an agent cannot run it at all.** The platform's environment component is described in [02-platform-components.md](02-platform-components.md), section 5.

Status: a draft standard from internal discussion on 2026-10-18; not yet applied to a project.

## 1. Levels

A project does not have to meet everything at once. The level it reaches decides what work agents may be given on it.

| Level | The repository provides | Agents may be given |
|---|---|---|
| 0. Not ready | The project cannot be built without a person's help | Reading and explaining code; drafting documents |
| 1. Builds | One command builds it from a clean machine | Changes checked by building only, with careful human review |
| 2. Unit-tested | One command runs unit tests, which pass on the main branch | Changes that unit tests can verify |
| 3. Runs with its services | One command starts the application with its dependent services and sample data; integration tests run | Features and fixes that integration tests verify |
| 4. End-to-end | End-to-end tests run against the started application | Features end to end; people check acceptance |
| 5. Deployable | Deployment to a test environment is automated and repeatable | Deployment to test environments; production stays behind approval |

## 2. Checklist

### Environment

- [ ] The environment is defined in the repository: a container image, dev container or compose file, plus a setup script. Nothing depends on a particular person's machine.
- [ ] Versions are pinned: language, SDK, tools, dependencies (lock files committed).
- [ ] Dependent services (database, cache, queue, storage) start in containers, or stand-ins are provided.
- [ ] Outside systems (third-party APIs, single sign-on, payment, email) have mocks or sandboxes, switched on by configuration.
- [ ] The environment starts without network access to production and without production credentials.

### Commands

- [ ] One command each, documented in the README, for: set up, build, start, unit tests, integration tests, end-to-end tests, lint and format.
- [ ] Each command exits with a non-zero code on failure and prints a readable reason.
- [ ] Commands run without interactive prompts.

### Tests and data

- [ ] Tests pass on the main branch, every time. Unreliable tests are fixed or marked.
- [ ] Sample data is synthetic or anonymised, committed or generated by a script, and loads with one command.
- [ ] The tests that cover each area of the code can be found (by folder or naming), so an agent knows what to run after a change.

### Configuration and secrets

- [ ] An example configuration file lists every setting with a safe value for testing; real values are never committed.
- [ ] Secrets are read from the environment or a secret store, never from files in the repository.

### Knowledge for agents

- [ ] A README that says what the system does, its architecture in brief, and how to run it.
- [ ] An instruction file for agents: coding standards, structure, conventions, what not to touch, how to verify a change.
- [ ] Architecture decisions recorded where agents can read them (in the repository or the knowledge base).
- [ ] Requirements and acceptance criteria linked from the work items, not only discussed in meetings or chat.

### Pipeline

- [ ] Continuous integration runs build, tests and lint on every pull request, with the same commands as above.
- [ ] Branch protection: no direct pushes to the main branch; merges need passing checks and an approving review.
- [ ] Deployment to test environments is scripted (level 5).

## 3. Projects that need a separate plan

Some projects cannot reach the higher levels in a container. Each needs its own decision on what agents may do:

| Kind of project | Obstacle | Typical approach |
|---|---|---|
| Mobile apps | Emulators needed; iOS builds need macOS | macOS build hosts, emulators in the pipeline; device testing stays with people |
| Windows desktop software | Windows build and UI test hosts | Windows hosts in the pipeline |
| Embedded systems, hardware | Real devices | Simulators where they exist; hardware tests stay with people |
| Legacy or customer-hosted systems | Behind a VPN, licensed software, no container image | Agents limited to levels 0 to 2 until an environment can be created |
| GPU, large data, many services | Cost and size of a full environment per task | A shared test environment, or a reduced set of services per task |

## 4. Using the standard

- Assess each project against the levels before an agent team is assigned, and record the level.
- Give agents only the work their project's level can verify.
- Raising a project's level is ordinary engineering work, and it helps human developers as much as agents: faster onboarding, reliable tests, repeatable deployment.
